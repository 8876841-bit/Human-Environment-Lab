# 06-入口协议

> 本文件用于规定 Human-Environment-Lab 的信息入口。  
> 目的不是让用户先做复杂分类，而是让每一条真实材料都有合适的去处，避免全部塞进同一个对话框。

---

## 一、核心判断

对话框不是唯一入口。

```text
对话框 = 临时推演入口
GitHub 仓库 = 长期记忆与骨架
GitHub Issue / 运行中台 = 状态追踪与分支管理
物理世界 = 真实输入与最终验证场
```

入口不是越多越好。

```text
入口越多，如果没有分工，系统越乱。
入口的作用不是增加负担，而是让不同阶段的材料各就各位。
```

本协议不要求用户每次先判断“这是什么类型”。

更适合的方式是：

```text
先收进来。
再决定怎么处理。
最后写回对应位置。
```

也就是说：

```text
用户负责带回真实材料。
数字生命负责辅助判断入口。
运行中台负责记录状态和收口。
```

---

## 二、入口不是分类表，而是动作表

每次有新东西进来，不先问“它属于哪一类”，而是先问：

```text
现在最需要做的动作是什么？
```

| 当前动作 | 推荐入口 | 目的 | 不适合做什么 |
|---|---|---|---|
| 先随手记一下 | 手机备忘录 / 微信文件传输助手 / 语音备忘录 | 快速捕捉，不让真实触发丢失 | 不做长期保存 |
| 让它正式进入系统 | `07-运行中台/01-真实触发收件箱.md` / GitHub Issue | 建档，获得编号和状态 | 不展开长篇推演 |
| 需要深聊和压测 | ChatGPT / Claude / 其他对话框 | 临时分析、拆解、反驳、生成假设 | 不承担长期记忆 |
| 需要长期追踪 | GitHub Issue | 保存单个问题的完整生命线 | 不混入多个大问题 |
| 需要看当前进度 | `07-运行中台/02-运行看板.md` | 判断继续、暂停、验证、收口 | 不写大段思考 |
| 暂时不追但不想丢 | `07-运行中台/04-分支停车场.md` | 停放对话中长出的新方向 | 不抢当前主线 |
| 已经形成阶段性结论 | `07-运行中台/03-对话收口模板.md` / 对应仓库文件 | 收口、写回、沉淀 | 不把临时猜测写成稳定事实 |
| 需要现实验证 | `07-运行中台/02-运行看板.md` / 现实行动记录 | 明确下一步现实动作 | 不停留在“继续观察” |
| 已经有现实反馈 | 原 Issue 评论 / 观察日志 / 运行日志 | 回收物理世界反馈 | 不只记录情绪评价 |
| 需要公开表达或交付 | 先做 Lab 交付判断，再进入 `05-内容生产体系/` 或具体平台 | 把 Lab 结果带回现实 | 不作为默认出口 |
| 后期自动化接入 | 表单、Dify、n8n、快捷指令、GitHub Actions | 批量化输入与同步 | 当前规则未稳定前不启用 |

## 三、最小入口组合

当前阶段只使用四个主入口。

```text
1. 手机备忘录
   用于随手捕捉真实触发。

2. 07-运行中台/01-真实触发收件箱.md 或 GitHub Issue
   用于让触发点正式进入系统。

3. ChatGPT 对话框
   用于深度推演、压测判断、生成临时假设。

4. GitHub 仓库
   用于保存状态、规则、文件、日志和长期记忆。
```

暂不优先启用：

```text
Notion
飞书多维表格
n8n
Dify 自动化
微信机器人
Telegram Bot
前端表单
```

原因：

```text
当前系统还在建立入口规则。
规则未稳定前，自动化会放大混乱。
```

## 四、标准流转

### 1. 最小流转

```text
物理世界真实触发
↓
手机备忘录 / 收件箱快速记录
↓
对话框进行临时硅基处理
↓
对话收口模板整理结果
↓
运行看板更新状态
↓
必要时进入现实行动 / 内部研究 / 表达交付 / 暂不表达
↓
物理世界反馈
↓
原 Issue / 观察日志 / 规则库回收
```

### 2. 更稳的流转

适用于会反复追踪的问题：

```text
物理世界真实触发
↓
收件箱记录
↓
创建 GitHub Issue
↓
对话框深度推演
↓
对话收口
↓
运行看板标状态
↓
现实验证或交付
↓
反馈写回原 Issue
↓
必要时更新规则库
```

## 五、什么时候必须开 GitHub Issue

出现以下情况，建议开 Issue：

```text
1. 这个触发点会被反复追问。
2. 它需要现实验证。
3. 它会产生多次反馈。
4. 它可能连接到一个长期母题。
5. 它不适合只放在收件箱里。
6. 它需要保存原话、截图、观察记录或后续行动。
```

Issue 标题格式：

```text
TRG-YYYYMMDD-001：一句话描述真实触发
```

示例：

```text
TRG-20260616-001：为什么很多建材人觉得过两年市场会变好？
```

## 六、什么时候进入对话框

对话框只在需要“临时硅基处理”时使用。

适合进入对话框的情况：

```text
需要拆解一个困惑。
需要压测一个判断。
需要区分事实、感受、猜测和结论。
需要生成临时假设。
需要把复杂东西说成人话。
需要对一个现实反馈做复盘。
```

不适合继续在对话框里绕的情况：

```text
没有新现实材料。
已经开始重复解释同一个概念。
已经形成下一步现实动作。
已经发现证据不足。
已经长出新方向但和当前主题无关。
已经可以收口写回仓库。
```

硬规则：

```text
对话框只负责临时计算。
对话框不负责长期保存。
对话结束必须收口。
```

---

## 七、什么时候停放分支

如果对话里出现新的方向，但它不是当前主线，进入：

```text
07-运行中台/04-分支停车场.md
```

停放格式：

```text
分支编号：
从哪个主题长出来：
一句话描述：
为什么暂时不追：
重新启动条件：
```

原则：

```text
不是所有好问题都要现在追。
当前主题没有收口前，不让新分支抢主线。
```

---

## 八、什么时候写回仓库

出现以下任意一种，就要写回仓库，而不是继续在对话框里扩：

```text
已经形成阶段性判断。
已经明确下一步现实动作。
已经识别出证据缺口。
已经需要暂停。
已经需要进入现实验证。
已经形成可复用规则。
已经发现旧规则需要修正。
```

写回位置：

```text
阶段性判断 → 03-对话收口模板.md / 对应 Issue
下一步动作 → 02-运行看板.md
新分支 → 04-分支停车场.md
现实反馈 → 原 Issue / 观察日志
稳定规则 → 规则库 / 系统内核 / 对应模块文件
```

---

## 九、什么时候不要新增入口

以下情况不要新增工具或入口：

```text
只是想换个地方继续聊。
当前触发点还没有状态。
上一个对话还没有收口。
新分支没有进入停车场。
没有现实反馈，只是在重复推演。
只是因为焦虑而想多建一个系统。
```

硬规则：

```text
没有收口，不开新入口。
没有状态，不继续深聊。
没有现实动作，不升级自动化。
```

## 十、入口之间的权力顺序

当不同入口发生冲突时，按这个顺序判断：

```text
1. 00-系统内核/：最高边界
2. CURRENT-MAINLINE.md：当前主线
3. STATUS.md：模块状态
4. RUNBOOK.md：日常运行方法
5. 07-运行中台/：状态控制与收口
6. GitHub Issue / 对话框：具体触发点处理
7. 05-内容生产体系/：只有表达传播时调用
```

如果对话框里的推演和系统内核冲突：

```text
以系统内核为准。
```

如果表达冲动和运行看板状态冲突：

```text
以运行看板状态为准。
```

## 十一、当前执行口令

旧口令废弃：

```text
这是新触发点、旧反馈、新分支、稳定规则、现实动作，还是表达交付？
```

废弃原因：

```text
它要求用户先做抽象分类，容易变成新的认知负担。
```

新口令：

```text
这条东西现在要先放哪里？
接下来要不要处理？
处理完写回哪里？
```

更短版本：

```text
先放哪？
要不要现在处理？
最后写回哪？
```

执行原则：

```text
用户不需要先分类。
系统负责辅助分流。
先让真实材料进入，再判断它应该继续、暂停、验证、交付还是归档。
```

---

## 十二、硬边界

```text
对话框不是唯一入口。
GitHub 仓库不是资料堆放处，而是长期骨架。
Issue 不是备忘录，而是单个触发点的生命线。
手机备忘录只是临时捕捉，不是长期系统。
自动化不是当前优先级。
内容平台不是默认出口。
没有状态的触发点不继续深聊。
没有收口的对话不进入下一轮。
```
