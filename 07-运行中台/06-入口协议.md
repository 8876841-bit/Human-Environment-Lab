# 06-入口协议

> 本文件用于规定 Human-Environment-Lab 的信息入口。  
> 目的不是增加工具，而是防止真实触发、深度推演、长期记忆、状态控制、现实反馈和表达交付混在同一个对话框里。

---

## 一、核心判断

对话框不是唯一入口。

```text
对话框 = 临时推演入口
GitHub 仓库 = 长期记忆与骨架
GitHub Issue / 运行中台 = 状态追踪与分支管理
物理世界 = 真实输入与最终验证场
```

入口不是越多越好。

```text
入口越多，如果没有分工，系统越乱。
入口必须按信息类型分工。
```

---

## 二、入口总表

| 信息类型 | 推荐入口 | 用途 | 不适合做什么 |
|---|---|---|---|
| 新真实触发 | `07-运行中台/01-真实触发收件箱.md` / GitHub Issue / 手机备忘录 | 快速捕捉现实触发 | 不做深度推演 |
| 单个触发点长期追踪 | GitHub Issue | 保存一个问题的完整生命线 | 不混入其他大问题 |
| 深度推演 | ChatGPT / Claude / 其他对话框 | 临时分析、压测、生成假设 | 不负责长期保存 |
| 长期记忆 | GitHub 仓库 | 保存协议、规则、状态、日志 | 不记录随手碎片 |
| 当前状态 | `07-运行中台/02-运行看板.md` | 判断继续、暂停、验证、收口 | 不写长篇推演 |
| 新分支 | `07-运行中台/04-分支停车场.md` | 暂存本轮不追的新方向 | 不抢当前主线 |
| 稳定规则 | 规则库 / 系统内核 / 对应模块文件 | 沉淀已验证判断 | 不写未经验证的推演 |
| 现实反馈 | 原 Issue 评论 / 运行日志 / 观察日志 | 回收物理世界反馈 | 不只看情绪评价 |
| 表达交付 | 小红书、抖音、B站、公众号、PDF、网页、私聊、线下沟通 | 把 Lab 结果带回现实 | 不作为默认出口 |
| 自动化输入 | 表单、Dify、n8n、快捷指令、GitHub Actions | 后期批量化接入 | 规则未稳定前不启用 |

## 三、入口选择规则

每次出现新信息，先判断它属于哪一类。

### 1. 新触发点

进入：

```text
07-运行中台/01-真实触发收件箱.md
```

或创建 GitHub Issue。

判断问题：

```text
这是一个新的真实触发，还是旧触发点的反馈？
它是否来自现实的人、事、关系、环境、行动或身体反应？
它是否需要长期追踪？
```

---

### 2. 旧触发点的新反馈

进入：

```text
原 GitHub Issue 评论
07-运行中台/02-运行看板.md
03-观察日志/
```

规则：

```text
旧问题的新反馈，不开新对话主线。
优先写回原触发点生命线。
```

---

### 3. 深度推演

进入：

```text
ChatGPT / Claude / 其他对话框
```

规则：

```text
一个对话只处理一个主问题。
对话框只负责临时计算，不负责长期保存。
对话结束必须用 03-对话收口模板.md 收口。
```

---

### 4. 新分支

进入：

```text
07-运行中台/04-分支停车场.md
```

规则：

```text
新分支不在当前对话展开。
先记录来源、描述、暂不追的原因、重新启动条件。
```

---

### 5. 稳定判断

进入：

```text
00-系统内核/
07-运行中台/
06-硅基数字生命工作流-V3/knowledge/
03-观察日志/
```

规则：

```text
没有现实反馈，不进入稳定规则。
没有证据边界，不写成事实。
稳定判断必须说明来源、适用范围和反例可能。
```

---

### 6. 现实行动

进入：

```text
07-运行中台/02-运行看板.md
```

状态通常是：

```text
S5 待现实行动
```

规则：

```text
现实行动必须具体到人、时间、动作、要观察的反馈。
不能只写“继续观察”。
```

---

### 7. 表达交付

进入：

```text
05-内容生产体系/
表达传播 Agent
平台发布入口
```

但必须先通过 Lab 交付判断。

规则：

```text
内容不是默认出口。
公开表达只是交付形式之一。
证据不足、关系风险高、隐私风险高时，优先内部研究或暂不表达。
```

## 四、最小入口组合

当前阶段只使用四个主入口。

```text
1. 手机备忘录
   用于随手捕捉真实触发。

2. 07-运行中台/01-真实触发收件箱.md 或 GitHub Issue
   用于让触发点正式进入系统。

3. ChatGPT 对话框
   用于深度推演、压测判断、生成临时假设。

4. GitHub 仓库
   用于保存状态、规则、文件、日志和长期记忆。
```

暂不优先启用：

```text
Notion
飞书多维表格
n8n
Dify 自动化
微信机器人
Telegram Bot
前端表单
```

原因：

```text
当前系统还在建立入口规则。
规则未稳定前，自动化会放大混乱。
```

## 五、标准流转

```text
物理世界真实触发
↓
手机备忘录 / 收件箱快速记录
↓
GitHub Issue 或 运行中台建档
↓
对话框进行临时硅基处理
↓
对话收口模板整理结果
↓
运行看板更新状态
↓
必要时进入现实行动 / 内部研究 / 表达交付 / 暂不表达
↓
物理世界反馈
↓
原 Issue / 观察日志 / 规则库回收
```

## 六、什么时候必须开 GitHub Issue

出现以下情况，建议开 Issue：

```text
1. 这个触发点会被反复追问。
2. 它需要现实验证。
3. 它会产生多次反馈。
4. 它可能连接到一个长期母题。
5. 它不适合只放在收件箱里。
6. 它需要保存原话、截图、观察记录或后续行动。
```

Issue 标题格式：

```text
TRG-YYYYMMDD-001：一句话描述真实触发
```

示例：

```text
TRG-20260616-001：为什么很多建材人觉得过两年市场会变好？
```

## 七、什么时候不要开新入口

以下情况不要新增工具或入口：

```text
只是想换个地方继续聊。
当前触发点还没有状态。
上一个对话还没有收口。
新分支没有进入停车场。
没有现实反馈，只是在重复推演。
只是因为焦虑而想多建一个系统。
```

硬规则：

```text
没有收口，不开新入口。
没有状态，不继续深聊。
没有现实动作，不升级自动化。
```

## 八、入口之间的权力顺序

当不同入口发生冲突时，按这个顺序判断：

```text
1. 00-系统内核/：最高边界
2. CURRENT-MAINLINE.md：当前主线
3. STATUS.md：模块状态
4. RUNBOOK.md：日常运行方法
5. 07-运行中台/：状态控制与收口
6. GitHub Issue / 对话框：具体触发点处理
7. 05-内容生产体系/：只有表达传播时调用
```

如果对话框里的推演和系统内核冲突：

```text
以系统内核为准。
```

如果表达冲动和运行看板状态冲突：

```text
以运行看板状态为准。
```

## 九、当前执行口令

以后每次新信息进入系统，先问：

```text
这是新触发点、旧反馈、新分支、稳定规则、现实动作，还是表达交付？
```

对应入口：

```text
新触发点 → 收件箱 / Issue
旧反馈 → 原 Issue / 观察日志
新分支 → 分支停车场
稳定规则 → 规则库 / 对应系统文件
现实动作 → 运行看板
表达交付 → 先做 Lab 交付判断，再进 05-内容生产体系
深度推演 → 对话框
```

---

## 十、硬边界

```text
对话框不是唯一入口。
GitHub 仓库不是资料堆放处，而是长期骨架。
Issue 不是备忘录，而是单个触发点的生命线。
手机备忘录只是临时捕捉，不是长期系统。
自动化不是当前优先级。
内容平台不是默认出口。
没有状态的触发点不继续深聊。
没有收口的对话不进入下一轮。
```
