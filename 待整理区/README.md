## 第零原则：融入，不是堆叠

> 这是本文件最重要的规则。比后面所有操作规则都重要。

**新内容加入系统的目的，不是"又多了一个文件"，而是让系统变得更准确、更完整、更像她最初想建的那个东西。**

Agent 处理新内容时，必须回答三个问题：

```text
1. 这个新发现，让系统的哪一部分变得更清楚了？
   → 它不是孤立的。它一定连接着已有的某个根基、某条母线、某个框架。

2. 它是在"补充"还是"深化"？
   → 补充 = 填补了一个空白区域
   → 深化 = 让一个已有的判断变得更不可撼动
   → 两种情况都要说清楚

3. 它有没有改变或挑战已有的 CORE？
   → 如果有，这是进步（新认识修正旧判断），需要明确指出旧判断哪里不够
```

**融入的具体做法：**

新内容不能只放在一个新文件里。必须追溯它应该到达的地方：

```text
新观察/新判断
    ↓
它是哪个层级？
    ↓
第一性原理层 → 写入 ROOT-LOCK（根基）
底层逻辑层   → 写入对应模块的执行文件
操作层       → 写入工作流/节点规范
活人感层     → 写入活人感随想库
```

一条新内容，可能同时到达多个层级。06-18 的"群体与个体感知差异"就是一个例子——它同时更新了 ROOT-LOCK（根基）、内容生成执行层（操作）、活人感随想（素材）。

**融入的检验标准：**

- 如果删掉这个新发现，系统会变弱吗？会 → 融入成功。不会 → 只是堆了一个文件。
- 这个新发现，和已有的根基是"互相印证"还是"互相矛盾"？互相印证 → 加强。互相矛盾 → 需要你判断哪个对。
- 三个月后回来看，这个发现还站得住吗？

## 两种入口，同一规则

本仓库接收的内容只有两类，但规则一样——都经过待整理区，都需用户确认。

**类型一：新素材/新输入**
- 用户提供的录音、灵感随记、聊天记录、外部资料
- Agent 进行三层处理（活人感随想 → 问题追踪 → 融入系统）
- 示例：06-18《群体与个体感知差异》→ 新增 ROOT-LOCK 九/十/十一 + 活人感随想 + 问题追踪

**类型二：体系优化**
- 用户主动发起的框架调整、规则补充、模块升级
- Agent 写修改方案 → 放待整理区 → 用户确认 → 融进 CORE 文件
- 示例：内容治理层建立（待整理区/ + STATUS-MANIFEST）、价值观表从 LEGACY 回收到 01-总定义

两种情况都遵循同一原则：**不是加文件，是让系统变强。** 不管是新素材还是体系优化，最终都落到"已有的哪个部分因此变得更准确、更完整"。

## 核心规则（三条，所有 Agent 必须遵守）

### 1. 新内容只能写进本目录

```text
所有 Agent 的新产出，默认只能写入 待整理区/。
不得直接写入或修改以下 CORE 目录中的任何文件：
  - 00-系统内核/
  - 01-观察框架/
  - 03-观察日志/
  - 04-账号矩阵/
  - 05-内容生产体系/
  - 09-内容与视频执行中台/
```

### 2. 写完后必须给出"合并建议"，不能直接搬进 CORE

Agent 处理完新内容后，必须在输出中明确告知：
- 这是全新内容，还是对已有内容的更新？
- 如果是对已有内容的更新，与哪些现有 CORE 文件冲突/重叠？
- 建议并入哪个目录、哪个文件？
- 哪些旧内容需要降为 LEGACY？

### 3. 只有用户确认后，Agent 才能搬进 CORE

```text
Agent 产出 → 写在待整理区 → 通知用户 → 用户确认 → Agent 搬进正式目录 + 更新状态清单
```

用户说"确认""可以推""搬进去"之前，任何内容不得离开本目录。

## 内容状态标签

每个文件必须在顶部声明状态：

```text
状态：DRAFT | CORE | LEGACY
```

| 状态 | 含义 | 谁可以写入 | 默认是否被检索 |
|------|------|-----------|--------------|
| `DRAFT` | 刚产出，待用户确认 | Agent 可写 | 否 |
| `CORE` | 已确认，当前有效 | 只有用户确认后才能 | 是 |
| `LEGACY` | 旧版本，历史参考 | 不可写 | 否（除非用户明确问） |

- 新文件默认 = DRAFT
- CORE 目录下的已有文件 = CORE（见 STATUS-MANIFEST.md）
- 同一个核心问题，只保留一份 CORE。新版本替代旧版本时，旧版本改标 LEGACY

## Agent 工作流程

### 核心原则：三层严格串行，不允许并行

```text
录音/新素材进入后，按三层严格串行处理。
每层有独立的完成信号和用户确认闸门。
上一层未确认，不得进入下一层。
```

### 三层串行流程

```text
步骤1: 活人感随想（保存原质）
  ├─ 把随想按原样保存，不加工、不提炼、不整理
  ├─ 保持她的质地——困惑、跳跃、未完成、有温度
  ├─ 完成信号：随想已完整保存，每条独立可调取
  └─ 闸门：用户确认"随想保存没问题" → 进入步骤2

步骤2: 问题追踪（逐条深挖）
  ├─ 每条问题独立分析，过四道深度门槛（见下方）
  ├─ 不能在分析问题A时脑子里已经在想问题B
  ├─ 完成信号：每个问题都过了四道门槛，标了 [已解决] 或 [长期开放]
  └─ 闸门：用户确认"每个问题的深度到了" → 进入步骤3

步骤3: 融入建议（判断去向）
  ├─ 哪些进 ROOT-LOCK（第一性原理层）
  ├─ 哪些进执行文件（底层逻辑/操作层）
  ├─ 哪些只作为活人感素材保留
  └─ 闸门：用户确认融入方案 → 搬进CORE目录
```

### 禁止行为

```text
❌ 禁止把三个步骤的产出写在一个文件里
❌ 禁止在步骤2完成前开始写步骤3的内容
❌ 禁止"因为要写多个文件所以压缩每个问题的分析时间"
❌ 禁止把"写完文件"当成完成标准——完成标准是"推到不能再推"
```

### 步骤2深度门槛（每个问题必须过四道）

```
门槛1：现象描述
  → 这个问题的具体表现是什么？
  → 给具体时刻/具体场景/具体感受
  → 不是抽象描述，是她真实经历的还原

门槛2：机制分析
  → 为什么会这样？底层机制是什么？
  → 推到不可再分为止（如果还能问"为什么"，就还没到）
  → 区分"相关"和"因果"——不是相关就分析

门槛3：反向检验
  → 如果反过来，结论还成立吗？
  → 有什么边界条件？什么情况下不适用？
  → 这个结论能用来预测/解释其他现象吗？

门槛4：连接已有
  → 它和已有ROOT-LOCK中的哪一条有关？
  → 是补充（填补空白）还是深化（让已有判断更不可撼动）？
  → 有没有改变或挑战已有CORE？如果有，需要明确指出
```

对标本库06-18问题-01（个体悲剧vs群体悲剧）的质量——它完整过了四道门槛。

### 步骤确认后的执行

```text
1. 接收用户任务
2. 按照三层串行流程逐层处理，每层等用户确认
3. 用户确认后 → 搬进正式目录，改标 CORE
4. 更新 /STATUS-MANIFEST.md
5. 提交时注明：哪些文件从 DRAFT 升为 CORE
```

## 冲突检查规则

Agent 在写内容前，必须检查：
1. 用户要讨论的话题，在现有 CORE 文件中是否已有答案？
2. 如果有，新内容是"补充"还是"替代"？
3. 如果是替代，旧内容是否需要降为 LEGACY？

不得在用户不知情的情况下创建与 CORE 冲突的内容。
